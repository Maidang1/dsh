# 产品设计与范围

## 1 产品目标

Harness Explorer 帮助第一次阅读 DeepSeek Harness 的用户理解两个问题：插件如何共同构成 Agent，以及单个插件的代码如何实现其职责。核心操作是从最小组合逐步添加插件，并对比添加前后的状态与数据流。

产品不以章节列表作为首屏主线。用户始终围绕当前插件树工作，学习步骤由选中的插件及当前实验决定。课程顺序可以提供建议，但不能取代自由探索树和观察运行。

## 2 第一版学习闭环

1. 打开最小对话组合，看到所有基础插件实例；基础节点可以折叠，但不能隐藏必需依赖。
2. 使用预置输入运行一次，看到模型请求、响应和会话记录。
3. 在插件库中选择提示词贡献插件，预览其依赖、作用域与预期影响。
4. 确认添加，生成新的实验版本；插件树显示新增实例和实际激活状态。
5. 进入该插件，使用 Code Hike 从入口、依赖、注册到清理逐步展开实现。
6. 对一个可运行阶段执行相同场景，记录该阶段实际产生的轨迹。
7. 对比前后请求，确认变化由本次注册贡献引起，而不是由动画脚本产生。
8. 查看该实现的职责边界、精简说明与上游源码链接。
9. 移除插件并重新运行，观察注册项和下一次请求恢复。

## 3 双层学习空间

### 3.1 整体实验台

中央是可展开的插件树。右侧是选中对象的摘要，底部是运行轨迹和数据对比。新增插件默认放在明确选择的作用域中；拖拽改变位置时，必须经过组合校验。

插件树的连线只表示组合层级。服务依赖、事件关系和实际数据流通过切换图层查看，使用不同线型和文字标签，不能只靠颜色区分。

### 3.2 单插件学习空间

点击“进入插件”后进入以 Code Hike 为主的布局：代码占主要宽度，内部架构与运行数据位于旁侧，整体插件树缩成可恢复的导航栏。

不在同一屏强行并排挤入插件树、内部架构、长代码、时间线和完整 JSON。提供两个主要模式：整体组合、插件实现。当前实例、场景和运行保持关联。

单插件视图包括：

- 实现步骤：上一步、下一步、跳转步骤、当前阶段是否可运行。
- 代码：当前完整文件、增量高亮、焦点区域、多文件切换。
- 架构：入口、服务接口、实现、注册项、事件、资源清理等实际存在的模块。
- 状态：挂载状态、依赖解析、已注册资源和最近执行检查点。
- 数据：输入、输出、请求片段及变化位置。
- 对照：精简教学代码与固定版本上游源码的映射。

## 5 添加与移除插件的交互

### 5.1 添加

1. 打开插件库，按职责筛选：提示词、工具、事件策略、模型适配、会话等。
2. 选择插件后显示依赖列表、兼容阶段、配置和来源。
3. 如果缺少依赖，明确显示缺少哪个服务、在哪个作用域解析。提供“同时添加依赖”操作，不能静默补齐后隐藏原因。
4. 提交变更只改变实验草稿。校验通过后生成不可变实验版本。
5. 新运行加载该版本；树上状态来自运行器报告。
6. 所有新增连线说明其类型，不从节点摆放位置推断服务关系。

第一版运行期间不更换代码或组合。用户可以修改草稿，但需结束当前运行后启动新版本。由此避免把每次阶段切换误作热更新。

### 5.2 移除

移除前列出受影响消费者与注册项。移除执行后记录清理行为，保留历史运行以供回放。是否导致消费者停用或等待，由锁定的行为契约决定，前端不自行推导。

### 5.3 依赖异常

“未启用”“等待服务”“加载失败”“无活动 Fiber”是不同情况。显示状态、原因和修复入口；没有证据时显示未知原因，不将所有非活跃状态归类为等待依赖。

## 6 运行和回放

第一版按钮使用“运行教学代码”，旁边标明“确定性模型”。这是真实执行精简实现，但不是默认调用真实模型，也不是完整上游运行。

运行结束后，默认显示最终状态。按“上一步”只移动回放游标。用户查看旧运行时，树、代码阶段和数据必须切换到该运行绑定的版本，或者显著提示当前草稿不同。

回放支持按事件、检查点、工具调用和状态变化定位。动画仅表现已经记录的传递关系，不能凭一条事件名称推断未观测的内部调用。

后续协作式执行单步使用独立按钮“暂停执行”“继续到下一检查点”。回放暂停与执行暂停必须有不同标签。

## 7 数据对比

比较运行 A 与运行 B 时展示输入、组合差异、阶段差异和场景版本。严格对照模式要求输入、模型脚本、初始数据、种子一致；不一致时允许并排查看，但不声称差异由单个插件导致。

支持四类对比：

| 对比对象 | 展示重点 |
|---|---|
| 注册表 | 新增、移除、覆盖的工具或提示词贡献 |
| 模型请求 | system 文本、messages、工具 schema 的变化 |
| 执行过程 | 新事件、拦截、错误与分支的变化 |
| 会话记录 | 新增持久事件、模型可见历史的差异 |

大对象先显示摘要，按字段展开。流式内容按请求分组；不把每个 token 的动画作为默认教学粒度。

## 8 插件内部架构内容

每个插件至少回答：职责是什么、由谁调用、依赖什么、拥有哪些状态、注册哪些资源、在哪些事件上工作、卸载清理什么。

节点可以代表文件、类、函数、类型或注册项。连接必须标明“调用”“实现”“注册”“读取”“订阅”“清理”等关系。不能为外观统一强行给每个插件编造入口、接口、实现三个文件。

架构说明区分代码事实与设计解读。设计解读应说明依据，如“消费方通过服务接口调用，因此可以替换实现”；不要把未经文档支持的动机写成作者原话。

## 9 第一版范围

第一版覆盖：最小对话组合、提示词贡献、工具注册与调用、一个事件中间件、卸载清理、逐步代码展示、轨迹回放、前后对比和源码映射。

最小组合分两类：框架实验的最小树，以及能完成一次对话的最小树。后者具体节点由依赖审查确定，不能照概念图直接认定只需四个插件。

暂不覆盖：任意 npm 插件安装、任意用户代码执行、生产级模型路由、远程 shell、持久化迁移、完整 HMR、多 Agent 协作、所有上游插件、多人同步与账户系统。

这些能力不在范围内并不意味着可以删掉相关语义后宣称完整兼容。课程与运行元数据都需要声明支持范围。

## 10 可用性和体验标准

- 默认中文解释，保留源码符号与事件名称，不随意翻译 API 名。
- 首屏能在不配置密钥的情况下完成一次运行。
- 键盘可完成选择插件、切换阶段、运行和回放。
- 提供树的文本列表替代视图；图节点有可读名称。
- 遵守减少动画设置，代码动画关闭后信息仍完整。
- 宽屏显示双栏；窄屏通过标签页切换，避免代码压缩到不可读。
- 当前运行版本、当前阅读阶段和回放位置始终可识别。
- 错误提示包含阶段、原因与可执行的恢复操作。
